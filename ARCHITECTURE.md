# Правила архитектуры

**Simple Architecture = Clean Architecture + VIPER.** Слои разделены по ответственности (Clean), каждый экран собран по схеме View + Presenter (VIPER). View === JSX + `usePresenter()`.

1. Слои: View — только JSX и вызов `usePresenter`; Presenter берёт данные из хранилища и готовит их; логика — в хуках с понятными именами.
2. Файл — не больше 120 строк. Исключений нет.
3. Дерево папок повторяет иерархию компонентов; у каждого компонента своя папка, в ней View и папка `logic`; вложенность не ограничена.
4. `components` включает переиспользуемые ниже по дереву компоненты: общие для всего приложения — в `src/components`; общие для одной ветки — в `components` этой ветки (на уровне их ближайшего общего предка); используемый одним родителем — подпапкой внутри этого родителя, а в `components` не лежит.
5. `SearchBar/SearchBar.tsx`, `SearchBar/logic/usePresenter.ts`.
6. Архитектура — абстракции, а не инструменты; правила не ослабляем ради скорости.
7. Бизнес существует внутри и вне приложения. Бизнес-логика = варианты использования = tasks. Task — plain function, имя — глагол (`toggleFavorite`, `loadShows`).
8. Tasks общаются со store напрямую (`getState` / `setState`) и не зависят от React. Presenter вызывает tasks, но не содержит бизнес-правил.
9. Вся JS-логика компонента лежит в его папке `logic/`: `usePresenter.ts`, остальные хуки, вспомогательные функции presenter и папка `tasks/`. Переиспользуемые tasks (и хуки) поднимаются по тем же правилам, что и компоненты: в `logic/` общего предка ветки, а для всего приложения — в глобальную `src/tasks/`.
10. Бизнес-логика, не связанная с UI (TVmaze, кэш, фильтр по жанрам, пагинация, избранное), живёт на backend (`server/`); frontend отвечает за UI, debounce и состояние экрана.

## Добавлено на практике
Пункты 1–10 — из лекций. Пункты 11–24 — уточнения под наш стек и решения проекта; пункты 25–33 — решения для авторизации и личного избранного (задание 3); пункты 34–38 — принципы лекции 3 (зависимости и store); пункты 39–40 — таймауты и ошибки запроса. Из лекции 2 в них следует только пункт 17 (task возвращает результат, а `loading`/`error` действия живут в presenter: пример `logout`). Пункты 18–21 и 25–33 — наша договорённость, а не требование лекции; при расхождении с курсом правим их, а не код вслепую.

11. Инфраструктурные папки `api/`, `store/`, `lib/`, `hooks/`, `tasks/` лежат в корне `src` рядом с `components`; папку создаём, когда в ней есть что положить.
12. Стили — CSS Modules рядом с компонентом (`ShowCard/ShowCard.module.css`). Состояние для CSS отдаём атрибутами (`aria-pressed`), а не классами из presenter: иначе presenter тянул бы стили.
13. `logic/usePresenter.ts` создаём только если есть что готовить (данные из хранилища, форматирование, обработчики). Пустой presenter-«прокладка» не нужен: чисто декоративные компоненты (`ShowListSkeleton`, `StateMessage`, `GenreChip`) живут без него и без папки `logic`. Как только в View появляется логика — выносим её в presenter.
14. Типы, общие для нескольких файлов (например `AsyncStatus`), объявляются один раз в месте-владельце и импортируются; копировать тип нельзя.
15. Импорты: вверх по дереву и в инфраструктуру (`api`, `store`, `lib`, `hooks`, `tasks`, `components`) — через алиас `@/` (= `src/`); внутри своей ветки (сам компонент и его дети) — относительные `./`, например `./logic/usePresenter`. Цепочки `../../` не используем.
16. Store хранит только данные. Зависимые изменения (новый запрос сбрасывает жанр и страницу) — это task, а не метод store. Уведомление в store — данные (`kind`, `showName`), текст собирает Presenter.
17. Task возвращает результат: `{ error: null, ... } | { error: code }`. Исключения из `api/` она ловит сама и превращает в код ошибки; отмена запроса ошибкой не считается. Presenter ждёт результат и решает, что показать (toast, текст ошибки, состояние кнопки). Состояние одного действия (`isPending`) живёт в presenter; в store — только то, что читают несколько компонентов.
18. Договорённость проекта: сменил параметр — вызови загрузку: task, меняющая параметры запроса (`selectGenre`, `goToPage`, `searchByTerm`), сама вызывает `loadShows()`. Реакции на изменение store (`useEffect` по полю) для запуска сценариев не используем: причина и следствие лежат в одной функции.
19. Договорённость проекта: optimistic UI и откат — внутри task: сначала меняем store, потом зовём `api/`, при ошибке возвращаем store и отдаём код ошибки (`toggleFavorite`).
20. Договорённость проекта: debounce — в presenter (хук `useTermDebounce` держит таймер и вызывает task), потому что это реакция интерфейса на ввод, а task остаётся функцией без скрытого состояния. Отмену устаревшего запроса делает `api/` (`fetchShowsPage` сам отменяет предыдущий): запрос из пагинации должен отменять и запрос из поиска, поэтому владелец отмены один.
21. Тексты для пользователя (ошибки, уведомления) делает Presenter по коду из task или из ответа сервера (`getErrorText`, `getToastText`), а не task, store или backend. Таймер автоскрытия toast — тоже в presenter.
22. Backend повторяет слои клиента без View: `routes/` (роль presenter: разобрать запрос, вызвать task, превратить результат в HTTP-ответ) → `tasks/` (бизнес-логика, не знает про Express и HTTP-статусы) → `storage/` (данные в памяти, простые методы без правил) и `api/` (запросы к TVmaze) + `lib/` (чистые функции). Лимит 120 строк и правила именования действуют и там. Срок жизни кэша проверяет task `getCached`, а не storage.
23. Между сервером и клиентом ошибки идут кодом (`{ error: 'upstream' }`) и HTTP-статусом, а не текстом. Типы и константы контракта API (`Show`, `ShowsPage`, `ErrorCode`, `MIN_QUERY_LENGTH`) лежат в `shared/` (`@shared/...`) и на клиенте и сервере не дублируются; список кодов ошибок тоже берём оттуда (`ERROR_CODES`), а не пересчитываем вручную.
24. Кэш, сессии и избранное хранятся в памяти сервера (`const cache = {}`, `const sessions = {}`, `const favorite = {}`); клиентского кэша выдачи нет, чтобы не расходиться с сервером. Избранное лежит по email: `favorite[email][id]`.
25. Авторизация — такой же сценарий, как остальные, и идёт по тем же слоям. Вход, выход и восстановление сессии — tasks (`login`, `logout`, `restoreSession`); кто вошёл — данные в `authStore` (`user`), без действий. Решает ли человек «вошёл он или нет», знает только backend: клиент держит токен и спрашивает, чей он.
26. Токен входа — не store и не task: его единственный владелец `api/session.ts` (как отмену запроса владеет `api/`). `request` сам добавляет `Authorization: Bearer`, поэтому ни task, ни presenter токен не передают. `localStorage` читает и пишет только `api/session.ts`, чтобы вход переживал перезагрузку.
27. Backend знает пользователя через `routes/requireUser`: роль presenter — достать токен из заголовка, спросить task `getSessionUser`, ответить `unauthorized` (401) или положить email в `res.locals`. Tasks получают `email` обычным аргументом и не знают ни про заголовки, ни про HTTP. Ключ, пришедший от клиента (токен), ищем только среди собственных ключей объекта (`Object.hasOwn`), иначе `constructor` и `__proto__` сойдут за существующий токен. Личные данные в `storage/` хранятся под ключом email; правило «один email — один человек» (`normalizeEmail`) живёт в task `createSession`.
28. Права проверяются дважды, с разной целью. Backend — единственный источник правды (`unauthorized`, 401). Task клиента (`toggleFavorite`) не отправляет запрос гостю и сразу возвращает `{ error: 'unauthorized' }`: это бизнес-правило сценария, а не украшение интерфейса. Presenter прав не проверяет, он только показывает результат (toast `login-required`) и прячет то, чем гость пользоваться не может (`FavoritesButton`).
29. Начало и конец сессии — общие tasks в `src/tasks/`: `startSession(user)` кладёт `user` в store и сразу грузит личные данные (`loadFavorites`), `endSession()` стирает токен, `user` и все личные store. Новый личный store добавляем в `endSession`, а загрузку его данных — в `startSession`: «сменился пользователь — вызови загрузку» (то же правило, что 18).
30. `unauthorized` из любого запроса значит, что сессии больше нет (сервер перезапускали): task вызывает `endSession()` и возвращает код, presenter показывает toast. Откат optimistic UI в этом случае не нужен: `endSession` и так очищает личные store. Так же и при смене пользователя за время запроса: task запоминает email до запроса и после него откат и служебные флаги трогает, только если пользователь тот же (`loadFavorites`, `toggleFavorite`, `clearFavorites`).
31. Страница — обычный компонент верхнего уровня (`src/LoginPage/`). Роутер (`HashRouter`, работает на GitHub Pages без настройки сервера) подключается один раз в `main.tsx`, маршруты описывает `App.tsx`, пути — константы в `lib/paths.ts`. Переход — JSX (`<Link>`, `<Navigate>`) по готовому флагу из presenter; императивный `navigate()` вызывает только presenter.
32. Корневой `App` устроен как остальные компоненты: его логика — в `src/logic/` (`usePresenter.ts`, `tasks/restoreSession.ts`). Стартовое событие «приложение запущено» (`restoreSession`) запускается из presenter через `useEffect` при монтировании: это событие, а не реакция на store (п. 18).
33. Пока неизвестно, гость ли это, страницы не показываем: иначе вошедший на секунду увидит экран гостя. Флаг «проверка идёт» нужен одному `App`, поэтому это `useState` его presenter, а не поле store (п. 36).
34. Направление зависимостей (лекция 3): файл, который меняется чаще, зависит от файла, который меняется реже (как в SOLID). Цепочка `Component → Presenter → Task → Store` идёт только вниз; между слоями лежит интерфейс: props и возвращаемое значение presenter для View, тип результата task для presenter. Нижний слой не импортирует верхний: store не знает про `api/`, task и React, `api/` не знает про store и tasks, task не знает про React и presenter. Тип, который нужен нижнему слою, лежит в нём самом или в `lib/` / `shared/` (`ApiErrorCode` в `lib/`), а не в верхнем.
35. Presenter читает store напрямую (селектор, `getState`), а пишет в store только task: чтение идёт в обход task, запись — никогда.
36. В store только глобальные данные и никакой логики. Глобальные — те, что читают несколько компонентов или что переживает компонент (выдача, избранное, `user`). Данные одного компонента (текст в форме, `isPending`, флаг «проверяем вход») лежат в `useState` его presenter.
37. Минимизация данных: store хранит первичное. Всё, что можно вычислить (счётчик, `isFavorite`, `isVisible`, тексты, подписи), считает presenter, а в store не кладём. Служебное состояние task, которое читают только tasks (`changes` у избранного), терпим, пока без него нельзя защититься от гонки запросов.
38. Минимизация обращений: подписываемся узким селектором (`state => state.user !== null`), а не на весь store, и возвращаем из него примитив или готовую ссылку, а не новый объект. `useXStore()` без селектора не пишем.
39. Запрос к нашему API не бывает бесконечным: `request` обрывает его через `REQUEST_TIMEOUT_MS` и отдаёт код `network`. Отмена вызывающего (`signal`) по-прежнему не ошибка. Иначе `App`, который ждёт `restoreSession`, показал бы пустую страницу, пока сервер просыпается.
40. Ошибка из-за самого запроса (битый или слишком большой JSON, статус 4xx у исключения) на сервере отвечает `bad-request` и в лог не попадает (`lib/isClientError`); в `handleUnexpected` остаётся только непредвиденное. Ограничения на входные данные (`MAX_EMAIL_LENGTH`, лимит тела) — часть контракта: константа в `shared/`, правило на сервере, подсказка (`maxLength`) на клиенте.
